## Provisioned common users

The supplied docs/maigha-users-for-upsilon.csv contains 40 valid, distinct Firebase UIDs. Its exact headers are firebase_uid,email,display_name. The export is treated as Maigha's approved provisioning list; validation checks its format, not the current status of every Firebase account.

Created public.users, shared by all four tools:

| Column | Purpose |
| --- | --- |
| id | Stable local UUID primary key, generated by explicit administrative insertion |
| firebase_uid | Required unique Firebase UID; length 1-128 |
| email / display_name | Optional profile information, not identity keys |
| created_at / updated_at | Required timestamps |

Initial import inserted 40 users. Re-import inserted 0, updated 0 and left 40 unchanged. Final read-only verification found 40 users, 40 distinct UIDs and 40 distinct local UUIDs. Matching is by exact UID, never by email. Emails are not unique and cannot merge accounts. Changed profile information updates only email/display_name and updated_at, preserving id and created_at. Blank profile fields become NULL. Missing rows in a later import do not delete users.

public.tools_schema_migrations records migration version, checksum and applied time. The first migration applied one change; repeating it applied none. Changed applied migration contents are rejected. A pre-existing unrelated public.users table causes failure rather than silent reuse.

## Explicit administrative commands

From services/tools-api:

```powershell
npm.cmd run users:seed -- --file ../../docs/maigha-users-for-upsilon.csv --dry-run
npm.cmd run db:migrate
npm.cmd run users:seed -- --file ../../docs/maigha-users-for-upsilon.csv
npm.cmd run test:provisioning
npm.cmd run test:provisioning:db
node scripts/review-legacy.js --verify
```

Dry-run only validates the file and never connects to the database. Migration and seed are separate explicit operations, not invoked at login or server startup. Each actual operation uses a transaction and a common administrative advisory lock. Failed imports roll back all writes. Duplicate UIDs, including identical duplicates, fail validation before database access.

The parser supports BOM, CRLF, quoted commas and escaped quotes. It rejects malformed quoting, unexpected columns, missing/invalid UIDs, duplicate UIDs, invalid optional profiles and oversized input. Errors identify record positions without printing private field values; normal output contains counts only.

Files added: migrations/001_common_users.sql, src/db/provisioning.js, scripts/migrate.js, scripts/seed-users.js, scripts/review-legacy.js and tests/provisioning*.test.js. Updated package.json scripts and root .gitignore. No backend auth/routes, frontend source, other tools or portal source changed in Phase 3.

## User isolation: not complete yet

The required rule is that user A cannot read user B's saved work. Provisioning alone does not enforce that rule. The current backend still uses JWT_SECRET verification, and its Mutual Fund read query filters only by client_id/tax_year, without a provisioned owner filter. Do not treat the existing API as owner-isolated or release it for shared-user use yet.

The Phase 2 frontend stays locked. Phase 4 will verify Firebase ID tokens and resolve public.users by verified UID. Phase 5 will enforce owner-scoped save/load. Login must never create a missing user automatically.
